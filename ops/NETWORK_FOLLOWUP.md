# 多线路调查与操作边界

2026-09-23 的只读核验中，千兆口 enp2s0 已具有自己的 DHCP 地址、经网关的默认路由，强制该接口的 route get 也选择了该接口地址。enp1s0 当前协商为 100Mbps 全双工，并非十兆。三条链路均显示 carrier，NetworkManager 与隧道服务处于 active。这些结果是时点证据，不表示长期稳定。

故障时间线（主机本地时间）：9月22日07:56:45 冗余脚本从 enp2s0 切至 enp1s0；19:45–19:46 NetworkManager 仍记录千兆口 `ip-config-unavailable` 和无租约；19:51:25 取得新 DHCP 租约，19:51:26 激活；19:51:51 冗余脚本重新选择千兆口。9月23日另有三次租约更新成功。因此应继续调查 DHCP/链路获取配置失败，不能把原因直接判定为线材性能。

`network_doctor.py` 收集地址、路由、规则、邻居、协商速率和服务状态。输出包含内部网络地址，原始文件仅留在维护目录，公开报告使用脱敏摘要。运行不续租、不改路由、不重启接口。

现有自动切换只证明绑定接口的 TCP 443 探测成功；它不证明 DNS、Cloudflare QUIC 或网站业务可用。隧道和应用分别使用 guardian 检查。禁止因普通 TCP 成功将其他故障标成 healthy。

后续现场窗口一次只改变一个变量：记录原端口与线缆标识，先交换线缆再交换路由器端口，分别观察 DHCP、carrier、丢包与 CRC 计数；保留另一条已验证线路及本机控制台。每次恢复原状态并记录结果。需要 DHCP 抓包时只捕获 UDP 67/68，保存在私有目录，不提交含主机标识的原包。禁止在远程唯一管理通路上直接断链演练。

本 PR 不替换运行中的冗余脚本，也没有实施上述硬件窗口。网络待办状态是“当前恢复，历史 DHCP 获取失败已确认，根因及长期稳定性待现场验证”。
